# Agent 自动化路线

更新时间：2026-08-06

## 1. 最终目标

本项目最终目标不是一个固定脚本，而是一个受控自动化求职 Agent。

理想工作流：

1. 用户点击“寻找岗位”。
2. Agent 在指定招聘平台搜索 AI 应用开发、Agent 开发、AI 后端等相关实习岗位。
3. Agent 采集候选岗位，去重，读取 JD，做岗位匹配评分和基于 JD 的本地风险判断。
4. 低匹配或命中 JD 高风险信号的岗位自动归档，并保存跳过原因。
5. 中间分数岗位保存为“待用户判断”，并生成建议询问点。
6. 高匹配、低风险岗位进入沟通候选；用户有投递意向时，可在岗位详情手动查询并复核公开公司资料。
7. 在允许的沟通模式下，Agent 可以向 HR 询问岗位相关信息，保存回复并重新评分。
8. 对方愿意继续且岗位仍高匹配时，Agent 整理投递理由和推荐简历版本。
9. 发送简历、上传附件、点击投递永远需要用户确认。
10. HR 提到面试后，Agent 标记为“面试邀请”；用户确认面试时间和形式后手动改为“待面试”，Agent 再开始面试准备。

## 2. 为什么不是脚本

脚本适合固定页面和固定按钮流程，但招聘平台存在登录、验证码、反爬、页面结构变化、HR 自然语言回复等不确定因素。

本项目需要的是：

- 状态机：每个岗位都有明确阶段和下一步动作。
- 工具层：浏览器扩展、Playwright、LLM、搜索、数据库分别承担不同职责。
- 决策层：规则先筛，LLM 做理解和生成，关键动作由用户确认。
- 审计日志：每一步搜索、评分、沟通、跳过和错误都可追踪。
- 安全边界：不托管密码，不绕过验证码，不自动发送敏感信息。

## 3. 系统架构

### 3.1 本地控制中心

现有 FastAPI + Jinja2 + SQLite 继续作为本地控制中心：

- 保存候选人画像、简历版本、岗位、候选岗位、沟通日志、面试准备和模型调用日志。
- 提供本地网页界面。
- 提供浏览器扩展调用的本地 API。
- 执行 JD 分析、评分、风险判断、话术生成和面试准备。

### 3.2 浏览器扩展

浏览器扩展是中期主路线。

用途：

- 运行在用户正常登录的 Edge/Chrome 中。
- 采集当前岗位详情页。
- 采集当前搜索结果页。
- 后续采集当前 HR 对话页。
- 把采集结果发送给本地应用。

边界：

- 不读取 Cookie、密码、验证码、请求头、本地存储或隐藏字段。
- 不截图。
- 不保存整页 HTML。
- 第一版不自动发消息、不自动投递。

### 3.3 Playwright 自动化

Playwright 用于长期受控自动化。

用途：

- 在独立的受控浏览器 profile 中自动搜索、打开岗位、读取消息、填写草稿和执行已确认动作。
- 用户需要为该 profile 登录招聘平台一次。
- 自动化 profile 不提交、不导出、不写入数据库。

边界：

- 不强行接管用户平时正在使用的普通 Edge。
- 不绕过验证码。
- 不在未确认时上传简历或点击投递。

### 3.4 LLM 决策层

LLM 负责理解、判断、生成和复盘，不直接操作网页。

LLM 输出结构化决策，例如：

```json
{
  "action": "ask_hr",
  "reason": "岗位匹配较高，但 JD 没写实习周期和到岗要求。",
  "message": "您好，想请问这个岗位的主要工作内容、技术栈和每周到岗要求是怎样的？"
}
```

本地策略层再判断该动作能否执行。

## 4. 平台和搜索范围

第一批平台：

- Boss 直聘
- 猎聘
- 实习僧
- 智联招聘
- 前程无忧

其中，当前 PC 消息自动化范围仅为 Boss 直聘、猎聘、实习僧。智联招聘和前程无忧继续用于岗位发现、JD 分析和投递准备，但不进入消息巡检、对话采集或自动回复，直到存在可验证的 PC 消息界面。

搜索关键词可由 Agent 自动扩展，并保存每次实际使用的搜索词。

默认关键词方向：

- AI 应用开发实习
- 大模型应用开发实习
- Agent 开发实习
- RAG 开发实习
- Python AI 后端实习
- AI 后端实习

城市优先级：

- 杭州
- 深圳
- 广州
- 上海
- 北京
- 成都
- 重庆

远程、线下、混合办公均可接受。

去重规则：

- 公司名 + 岗位名 + 平台 + 链接。
- 同公司同岗位跨平台保留，但标记为“疑似重复”。

默认搜索上限：

- 每个平台最多采集 20 个候选。
- 每轮总候选最多 100 个。
- 上限后续可在设置中调整。

## 5. 岗位评分和分档

前 2-3 轮搜索为观察期：

- 只采集、评分、统计分数分布。
- 不自动发消息。
- 不固定高/中/低阈值。
- 用真实岗位结果校准评分模型和分档线。

评分维度：

- 技术匹配
- 成长性
- 薪资
- 地点与时间
- 公司风险：初筛仅使用 JD 风险词和黑名单；公开公司资料由用户在有投递意向时手动查询
- 岗位真实性 / 招聘认真程度

岗位真实性重点判断：

- JD 是否具体。
- 是否包含真实工程内容。
- 是否像技术岗位，而不是包装成 AI 的销售、运营、培训或标注。
- 公司招聘行为是否可疑。

分档动作：

- 高匹配、低风险：进入沟通候选。
- 中间分数：保存为“待用户判断”，可生成建议询问点但不发送。
- 低匹配或高风险：自动归档，并保存跳过原因。

低分跳过原因必须保存，例如：

- 技术栈不匹配。
- 偏销售、运营、客服、标注或培训。
- 薪资、城市或实习时间不合适。
- 公司信息不足。
- 命中培训费、贷款、押金等风险信号。

## 6. 自动沟通模式

只保留三个模式。

### 6.1 关闭

什么都不做：

- 不监听。
- 不分析 HR 回复。
- 不生成草稿。
- 不发消息。

用户仍可手动使用 JD 分析、岗位列表和面试准备等非自动沟通功能。

### 6.2 草稿模式

允许：

- 采集和分析 HR 回复。
- 生成待发送消息。
- 放入待发送队列。

必须用户确认后才发送。

### 6.3 自主询问模式

允许 Agent 在规则范围内自动问岗位相关问题。

默认限制：

- 最多自动追问 2 轮。
- 超过 2 轮后暂停，等待用户选择是否继续。
- 只能围绕岗位、求职和面试流程沟通。
- 不回答与岗位无关的问题。

允许自主询问的内容：

- 工作内容。
- 技术栈。
- 实习周期。
- 每周到岗天数。
- 是否有导师。
- 是否接受大二。
- 薪资范围。
- 远程、线下或混合办公。
- 面试流程。

强制转人工：

- 联系方式。
- 面试时间。
- 发简历或上传简历。
- 薪资谈判。
- 线下地址确认。
- 身份证、银行卡等敏感信息。
- 押金、培训费、贷款等风险内容。
- 明显闲聊。
- 与岗位无关的问题。

## 7. 待发送队列

每条待发送消息至少包含：

- 岗位。
- 平台。
- 公司。
- HR 或会话标识。
- 生成原因。
- 消息正文。
- 模型和生成时间。
- 风险提示。

支持操作：

- 发送。
- 编辑后发送。
- 驳回。
- 标记为需要我处理。
- 归档岗位。

自动发送上限：

- 默认每天最多自动发 5 条第一轮询问。
- 默认每个平台每天最多自动发 3 条第一轮询问。
- 两个上限都允许用户手动修改。

Agent 自动发出的完整消息需要记录到岗位详情或沟通日志中。

## 8. HR 消息采集和巡检

### 8.1 手动对话采集

用户打开某个平台聊天页，浏览器扩展采集当前打开的 HR 对话。

聊天页采集范围：

- 采集当前打开的 HR 对话中已加载的全部消息文本。
- 不采集截图、Cookie、本地存储、请求头、隐藏字段或其他会话内容。
- 不批量采集所有 HR 聊天。
- 默认将当前对话已加载消息全部提供给 LLM，帮助避免重复询问和重复回答。
- 如果单个对话超过上下文或成本限制，则自动压缩为：岗位摘要 + 最近消息 + 历史摘要。

### 8.2 页面实时监听

用户打开招聘平台聊天页时，扩展可以监听当前页面的新消息。

前提：

- 电脑开着。
- 本地应用运行。
- 浏览器页面保持登录并打开。

### 8.3 受控自动巡检

当前已接入受控 Edge dry-run 巡检最小版。它会连接应用打开的专用 Edge 调试窗口，读取已打开的招聘平台聊天页可见文本，并交给 observation 接口做本地差分。

使用方式：

1. 在“沟通草稿”或“设置”页点击“打开 Edge 巡检窗口”。
2. 在该受控 Edge 窗口登录招聘平台。
3. 打开一个或多个 HR 对话页。
4. 点击“巡检当前 Edge 聊天页”，或开启定时巡检。

当前行为：

- 只读取当前已打开的招聘平台聊天页。
- 只读取页面可见文本。
- 默认 dry-run，不保存聊天全文，不生成草稿，不调用模型。
- 只写巡检统计和不含聊天正文的审计记录。
- dry-run 差分只保存清洗后文本的哈希指纹和更新时间，不保存聊天正文。
- 沟通模式关闭时不读取浏览器页面。
- 自动化暂停时，定时巡检和会生成草稿的采集会跳过；用户手动点击的 Edge dry-run 巡检仍可执行只读差分。

后续可继续扩展为 Playwright 使用已登录的专用 profile 定时进入消息列表、打开未读会话并做差分。

默认巡检频率：

- 活跃找实习：60 秒一次。
- 普通模式：5 分钟一次。
- 高频临时模式：30 秒一次。
- 夜间或暂停：不巡检。

成本规则：

- 巡检本身只做浏览器读取和本地差分，不调用 LLM。
- 没有新消息时，token 消耗为 0。
- 只有检测到新 HR 消息时才触发 LLM。
- LLM 输入只包含新增消息、岗位摘要、必要上下文和候选人画像摘要。
- 页面长文本不进入消息巡检 prompt。
- 每个会话设置 cooldown，避免同一消息反复调用。

### 8.4 巡检 observation 接口层

已新增本地接口：

```text
POST /api/message-patrol/observations
```

用途：

- 供浏览器扩展监听器、Playwright 或其他受控浏览器执行器上报“已观察到的当前对话可见文本”。
- 默认 `dry_run=true`，只做本地清洗、岗位匹配、重复差分和巡检统计。
- `dry_run=true` 时不创建 `conversation_captures`，不创建 `message_drafts`，不调用 LLM，不保存聊天全文。
- 为避免同一页面反复被判为新内容，dry-run 会保存清洗后文本的哈希指纹，不保存正文。
- 只有显式传入 `dry_run=false` 时，才进入现有“对话采集 -> 分类 -> 待确认草稿”流程。

请求示例：

```json
{
  "executor": "browser_extension",
  "dry_run": true,
  "trigger_type": "executor",
  "observations": [
    {
      "url": "https://www.zhipin.com/job_detail/example.html",
      "title": "某公司 HR 对话",
      "platform": "Boss 直聘",
      "text": "当前页面已加载的可见对话文本"
    }
  ]
}
```

响应会返回：

- `checked_count`
- `new_count`
- `skipped_count`
- `error_count`
- 每条 observation 的 `status`、匹配岗位、重复采集 ID 或新建采集 ID。

安全边界：

- 接口不接收 Cookie、localStorage、请求头、密码、验证码或截图。
- 默认 dry-run 不保存聊天全文。
- 沟通模式为“关闭”时不保存、不分析、不生成草稿。
- 自动化暂停时，后台/定时 observation 只写元数据巡检记录，不分析对话内容；`manual_browser` dry-run 属于用户主动只读检查，可以继续执行差分。
- 发送消息、发简历、投递仍然必须用户确认。

## 9. 简历和个人信息边界

允许 Agent 引用：

- 公开 GitHub。
- 公开项目链接。
- 专业。
- 年级。
- 当前求职方向。
- 候选人画像中明确填写的技能和项目事实。
- 通过“刷新 GitHub 项目资料”读取的公开 README、语言和最近提交，只作为项目事实证据，不自动推断为熟练技能。

具体学校名称只在候选人画像中明确填写后使用。

每周到岗天数、实习周期、城市偏好等信息：

- 不主动一上来全部发送。
- 优先询问对方岗位要求。
- 如果 HR 问到，可以按候选人画像回答。

技术能力回答规则：

- 候选人画像里有的，用“了解”“较熟悉”“有项目实践”等不夸大的词。
- 候选人画像里没有的，可以说“正在学习”或转给用户确认。
- 不使用“精通”等夸大措辞。

永远需要用户确认：

- 发送或上传简历。
- 发送简历链接。
- 点击投递。
- 发送手机号、邮箱、微信。
- 发送身份证、银行卡等敏感信息。
- 确认面试时间。
- 接受 offer。
- 填写真实个人信息表单。

## 10. 模型调用和成本控制

模型路由采用配置优先和项目内测评决定。

当前候选模型：

- `deepseek-v4-flash`：主力候选，适合高频任务。
- `deepseek-v4-pro`：复杂判断和复核候选，但不预设一定优于 Flash。
- `gpt-5.5`：高价值、复杂、敏感或面试相关任务候选。
- `gpt-5.6 terra`：高价值、复杂、敏感或面试相关任务候选。
- 本地 Ollama DeepSeek 小模型：只作为低风险预处理候选，实测不稳定时默认不用。

观察期需要做项目内评测：

- 用同一批真实 JD 跑不同模型。
- 用同一批 HR 回复跑不同模型。
- 用风险样例对比误判率。
- 记录准确性、稳定性、速度和 token 成本。
- 再决定最终模型路由和分数阈值。

推荐初始分工：

| 任务 | 默认模型 | 升级或复核模型 |
| --- | --- | --- |
| 页面类型判断 | 本地规则 | DeepSeek Flash |
| 搜索关键词扩展 | DeepSeek Flash | 无 |
| 候选去重和低质量过滤 | 本地规则 | DeepSeek Flash |
| JD 结构化抽取 | DeepSeek Flash | DeepSeek Pro |
| 岗位初评分 | 规则 + DeepSeek Flash | DeepSeek Pro |
| 公司公开风险查询 | 用户手动触发的网页检索 | 后续可选 LLM 摘要复核 |
| HR 新消息分类 | 本地规则 + DeepSeek Flash | DeepSeek Pro |
| 自动追问话术 | DeepSeek Flash | DeepSeek Pro |
| 即将自动发送的消息 | DeepSeek Pro | GPT-5.5 / GPT-5.6 terra |
| 面试准备 | DeepSeek Pro | GPT-5.5 / GPT-5.6 terra |
| 面试复盘 | DeepSeek Pro | GPT-5.5 / GPT-5.6 terra |
| 定时巡检 | 不调用模型 | 有新消息才调用 Flash |

硬规则：

- 浏览器巡检、页面差分、消息去重默认不调用 LLM。
- 高频任务优先用本地规则、Ollama 或 DeepSeek Flash。
- 涉及自动沟通、风险判断、边界判断时，用 DeepSeek Pro 复核。
- GPT-5.5 / GPT-5.6 terra 只用于高价值、复杂、敏感或面试相关任务。
- 不把完整网页和完整聊天历史反复发送给模型。
- 自动沟通使用“低成本模型先判断，高能力模型复核”的机制。
- 出现投简历、面试、薪资、身份证、押金、培训费等关键词时，必须升级复核或转人工。

日志保存：

- 任务类型。
- 平台。
- 模型。
- token。
- 费用估算。
- 结果摘要。
- 决策结果。
- 错误信息。

默认不保存完整 prompt、input、output。

调试模式下才允许临时保存完整输入输出，并且用户可以关闭和清理。

未来可添加每日成本阈值：

- 超过阈值后暂停自动回复。
- 只继续只读采集和本地差分。
- 阈值由用户自行设置，不内置强制默认值。

## 11. 面试状态和准备闭环

面试相关状态：

- 已沟通
- 面试邀请
- 待面试
- 面试准备中
- 已面试
- 面试复盘

状态含义：

- 面试邀请：HR 提到面试、笔试或约时间，但时间、形式或流程尚未确认。
- 待面试：用户已经和 HR 确认时间、形式和基本流程。
- 面试准备中：Agent 已开始生成或维护准备材料。
- 已面试：面试结束，等待结果或准备复盘。
- 面试复盘：记录没答好的问题和后续加强计划。

识别到面试邀请后：

- 标记岗位为“面试邀请”。
- 不自动回复面试时间。
- 不自动生成面试准备材料。
- 提醒用户去确认时间、形式和要求。

用户手动改为“待面试”后：

- Agent 开始生成面试准备。
- 生成 JD 技术点拆解。
- 生成项目可能追问。
- 生成 3 天冲刺计划。
- 生成 7 天准备计划。
- 生成模拟面试题。
- 当前第一版已实现：本地创建面试准备记录，不自动确认面试时间，不调用模型，重复保存状态不会重复创建。
- 生成不夸大的项目介绍。

线上面试支持边界：

- 先做面试前准备、模拟面试和面试后复盘。
- 不做实时替答或实时作弊式辅助。
- 已接入本地 ASR 做录音转写复盘：支持上传本地录音，使用 faster-whisper 的 CPU `int8` 推理；首次选择模型时下载到 `private/whisper_models/`，之后复用缓存。转写文本会并入面试准备，但不会上传录音或文本到第三方服务。

面试复盘需要保留“没答好的问题库”，用于后续加强模拟面试。
当前第一版已实现：面试准备详情页可手动记录薄弱点、状态和补强计划；同岗位后续准备会带入仍为“待练习”的薄弱点。

当前第二版已实现：用户可在面试准备详情手动触发“智能强化准备”。它按 `interview_prep` 模型路由，以 JD、候选人已填写的技能/项目、选定简历的去联系方式文本和待练习薄弱点为上下文，更新本地 3 天/7 天计划、题库与 Markdown。模型未配置、输出无效或调用失败时保留原有材料；不会自动触发，也不会参与线上面试实时回答。

## 12. 阶段路线

### V0.2 浏览器扩展采集 MVP

目标：

- 在用户正常登录的 Edge/Chrome 中采集当前页面。
- 不重复登录。
- 不自动沟通。
- 不投递。

范围：

- 新增本地采集接口。
- 新增浏览器扩展目录。
- 扩展按钮：采集当前岗位。
- 扩展按钮：采集搜索结果。
- 采集当前岗位后创建岗位并进入分析。
- 采集搜索结果后创建候选列表，不逐条抓 JD。

安装方式：

- 第一版使用开发者模式加载本地 `browser_extension/` 目录。
- 后续再考虑打包。

### V0.3 对话采集与草稿模式

目标：

- 用户打开 HR 对话页。
- 扩展采集当前对话。
- Agent 分析 HR 回复。
- 生成待发送队列。
- 用户确认后发送。

不做：

- 自动回复。
- 自动巡检全部会话。
- 自动投递。

### V0.4 自主询问模式

目标：

- 全局开启自主询问。
- Agent 自动问岗位相关问题。
- 默认最多 2 轮。
- 敏感、非岗位、面试时间、简历投递等内容转人工。

### V0.5 受控自动搜索与消息巡检

目标：

- 用户点击“寻找岗位”。
- Agent 跨平台搜索。
- 每个平台最多 20 个候选。
- 每轮总候选最多 100 个。
- 定时消息巡检。
- 有新消息才调用 LLM。

### V0.6 受控自动投递准备

目标：

- 高匹配、低风险岗位进入投递候选。
- Agent 整理投递理由。
- Agent 推荐简历版本。
- 用户确认后才投递或发简历。

当前第一版已实现：按“必投/可投递”且“低/低风险”筛选本地候选、推荐简历版本、保存投递理由和用户备注。用户确认后只更新本地为“待投递”，不自动上传简历、不点击投递、不发送消息；可从顶部导航或沟通草稿页顶部进入“投递准备”。

当前第二版已实现：对已确认的待投递岗位，在受控 Edge 打开来源页并做只读结构探测。探测只记录页面身份与控件数量，不保存页面正文，不填写字段、不上传简历、不点击投递。

当前第三版已实现：用户可在本地投递准备中编辑可选投递附言。只有已确认的待投递岗位、受控 Edge 页面身份唯一匹配、页面存在唯一附言/自我介绍输入框且用户输入确认短语后，系统才会填入这段附言。不会上传简历、不会点击投递或提交表单；验证码、身份信息、费用或多个页面/控件候选都会停止操作。

沟通侧已实现受控填入最小版：单条“待确认”的岗位沟通草稿必须通过发送闸门、用户输入确认短语，并重新匹配受控 Edge 当前聊天页的域名、岗位线索、输入框和发送按钮候选后，才会填入输入框。浏览器探测区的“前往待发送草稿（填入 Edge）”会跳到对应控制。该动作不会点击发送，不上传简历，不提交表单；命中简历、联系方式或付费等敏感文本会停止。

### V0.7 面试闭环增强

目标：

- 面试邀请识别。
- 待面试后自动准备。
- 模拟面试。
- 面试复盘。
- 没答好问题库。
- 本地 ASR 录音转写。

V0.4 第四块已实现：单会话巡检记录层。扩展采集当前对话时会记录一次巡检批次，包含检查数、新内容数、跳过数和错误数，但不保存聊天全文。
V0.4 第五块已实现：定时巡检 dry-run 执行器。可配置启停、间隔和手动 tick cooldown；启用后会尝试读取受控 Edge 已打开的招聘平台聊天页，只做本地差分，不调用模型。
V0.4 第六块已实现：浏览器巡检 observation 接口层。外部执行器可以上报对话可见文本；默认 dry-run 只做差分和统计，不保存聊天全文、不生成草稿、不调用模型。
V0.4 第七块已实现：受控 Edge 巡检窗口入口和手动 dry-run 巡检按钮。
V0.4 第八块已实现：待面试自动准备。岗位状态改为“待面试”或“面试准备中”时，会创建本地面试准备记录并在岗位详情页展示入口。
V0.7 第一版已实现：面试准备会提供题库和薄弱点库；模拟面试可逐题记录答案和结果，没答好会创建或更新待练习薄弱点，答得不错会标记对应薄弱点为已补强。该流程完全本地执行，不调用模型。
V0.7 第二版已实现：待面试后的基础材料可由用户手动用模型强化，生成仍基于明确候选人事实，模型调用记录 token 统计，审计日志不保存 JD、简历或转写正文。

候选校准报告已实现：它只读聚合本地候选反馈的覆盖率、平台分布、期望分流、详情待补充数量和最近误判样本，不调用模型、不自动改写筛选规则，也不访问招聘平台。真实平台样本仍是调整规则的唯一依据。

岗位深度匹配复核已实现：用户可在岗位详情手动调用 `job_match` 模型路由，以 JD、候选人明确事实与本地规则结果获得补充性匹配证据、缺口和沟通前待确认问题。每次成功结果独立保存为本地历史记录；它不修改本地评分、推荐、风险、状态或投递准备，且审计日志不保存 JD 或简历正文。
