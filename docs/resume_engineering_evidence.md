# 简历工程证据笔记

更新时间：2026-08-16

用途：沉淀后续简历、项目介绍和面试复盘可引用的工程事实。内容包含已验证的设计、未验证边界和验证证据，不等于可直接照抄的宣传文案。

## 项目事实

- 项目：`ai-intern-apply-agent`，面向 AI 应用开发、Agent 开发和 AI 后端实习的本地单用户求职 Agent。
- 主要技术：Python、FastAPI、Jinja2、SQLite、OpenAI-compatible API、浏览器扩展、Microsoft Edge CDP、faster-whisper。
- 主线：岗位发现 -> JD 分析与匹配 -> 受控沟通 -> 投递准备 -> 面试准备与复盘。
- 隐私与安全：不提交 API Key、Cookie、真实简历、SQLite、录音或聊天正文；不绕过登录和验证码。

## 工程问题、取舍与证据

### 1. 动态招聘页面与浏览器会话

- 问题：招聘平台依赖登录、动态渲染和易变 DOM。短生命周期浏览器接管会影响页面稳定性，直接读日常浏览器又有隐私和误操作风险。
- 方案：使用独立的受控 Edge profile，并以原生 CDP WebSocket 执行页面读取、岗位发现、探测与受控填入。普通 Edge 不接入；登录态仅留在浏览器 profile，不写入数据库或 Git。
- 已验证：搜索、JD 读取、聊天巡检、投递页面探测均有 CDP 回归测试；已知临时断连只对搜索和 JD 读取重试一次，绝不重试登录、验证码、消息或投递。
- 边界：尚不能承诺所有平台的登录状态、反爬或 DOM 改版都能长期稳定。

### 2. 搜索结果不是 JD，整页文本也会污染候选数据

- 问题：搜索卡片中的公司、薪资、摘要会错位或缺失；整页文本会混入导航、推荐和历史内容。
- 方案：先按详情链接、标题可读性和 AI 研发相关度做候选过滤，再逐个读取详情并单独抽取 JD、薪资与匹配度。详情不可可靠读取时标为“详情待补充”，不假装已得到 JD。
- 已验证：候选保存来源、摘要、错误和反馈；候选校准报告统计正确/误判与详情待补充数量；薪资解析测试避免将月薪和未披露薪资误判为低日薪。
- 边界：不同平台卡片结构差异大，筛选分档需要继续用真实 JD 样本校准。

### 3. token、隐私与判断质量的分层

- 问题：反复把完整搜索页或聊天历史发给模型成本高，也扩大隐私暴露；纯规则又无法处理 JD 语义和沟通意图。
- 方案：本地规则负责链接过滤、JD 风险词、薪资条件、文本差分和去重；模型只用于 JD 抽取/复核、深度匹配、话术和面试准备。公司公开研究延后到用户表达投递意向后手动触发。
- 已验证：dry-run 巡检只保存清洗文本的哈希与统计，不保存正文、不调用模型；无新内容时 token 消耗为零。模型调用按任务路由并记录模型、token、成本估算与结果摘要。
- 边界：模型输出只是补充证据，不能替代候选人事实、用户确认或安全规则。

### 4. 不可逆动作需要状态机、安全闸门和审计

- 问题：沟通、发简历和投递一旦执行会产生真实后果，不能让模型回答直接变成网页点击。
- 方案：岗位、投递准备、消息草稿和面试准备分别持久化；对沟通/投递动作检查岗位匹配、风险、内容、轮次、平台、页面身份、控件唯一性和敏感信号。附言仅在确认短语后预填，仍不上传简历、不提交表单。
- 已验证：回归测试覆盖面试邀请拦截、低匹配岗位拦截、敏感页面阻断、唯一目标页要求和填入后二次校验；审计日志保留决策结果，不保留敏感正文。
- 边界：自动上传简历、表单填写和点击投递尚未实现，不能描述为已完成。

### 5. 平台能力以真实观察为准，及时收缩范围

- 问题：实习僧 PC 端消息页可查看但不能可靠回复。若仍进入自动沟通白名单，会产生无法完成的发送路径。
- 方案：将实习僧从 PC 巡检、草稿填入和自动发送中移除，但保留岗位发现、JD 分析和投递准备；移动端回复由人工完成。
- 已验证：新增测试确认实习僧页面不被巡检读取、不进入聊天页自动化校准；Boss 直聘和猎聘保留 PC 沟通能力。
- 工程含义：能力白名单应来自真实可验证的产品约束，而不是为“多平台”而虚构兼容性。

### 6. 尚无真实相关 HR 对话时的验证策略

- 当前事实：已有消息主要是群发式“投递/感兴趣可聊”内容，尚未获得与目标岗位强相关的真实对话闭环。
- 可验证：用脱敏或合成场景覆盖消息分类、岗位关联、群发/无关内容分流、面试邀请转人工、两轮上限、消息差分、唯一页面定位和发送闸门。
- 不可声称：未验证“真实未读发现 -> 自主沟通 -> 真实面试邀请”的完整闭环；群发消息也不能当作有效 HR 沟通成功率。
- 样本策略：群发消息是“无需回复/无关内容”的负样本，人工标注后用于校准，不触发自动回复。

### 7. Agent 产品形态：对话控制层 + 可审计驾驶舱

- 判断：Agent 不等于只保留一个聊天框。纯聊天适合表达目标、追问和解释，不适合比较多个岗位、查看风险证据、管理简历版本或确认不可逆动作。
- 现状：驾驶舱承担数据编辑、表格比较、状态流转、审计和人工确认。
- 已实现：本地规则将“找杭州的 Agent 实习，日薪至少 200”等输入解析为有限 intent 与结构化筛选条件。低风险的“岗位搜索 -> JD 读取 -> 本地评分”由聊天指令直接调用既有受控服务；会发送消息、投递、上传简历或修改沟通反馈的动作先写入待确认计划。控制层会保存脱敏输入、解析依据、计划和审计结果，并链接回岗位、投递、沟通等驾驶舱页面。
- 演进：聊天直执行只允许非提交型浏览器任务，允许打开搜索页并写入本地岗位记录，但不允许模型自由操作浏览器。每次执行仍保存脱敏任务文本、结构化筛选条件、受限执行模式、结果摘要和审计决策；发送、投递与敏感信息仍保留人工确认。
- 安全原则：聊天层不直接操作浏览器，所有外部动作继续走既有服务、闸门和审计。
- 可验证：FastAPI 端到端测试覆盖“自然语言 -> 立即执行受控岗位发现 -> 结果和审计落库”以及“群发负样本 -> 确认后更新本地反馈”。
- 未验证边界：规则解析只覆盖明确的本地任务语法；未将真实 HR 正文作为控制层成功率证据，也未开放 LLM 自由工具调用或浏览器直接控制。

### 8. 未读会话发现的最小隐私边界

- 困难：从消息列表发现未读比巡检当前已打开会话更容易误把导航提醒、职位推荐或全局通知当成招聘方未读消息；同时不能为了提高命中率而读取会话正文或自动打开会话。
- 已实现：受控 Edge 只读扫描仅针对 Boss 直聘、猎聘的已打开页面，依据 DOM 结构属性和未读/红点标记统计候选会话。数据库保存平台、计数、标记类别、探测版本和审计摘要，不保存页面正文、会话名称、页面标题或链接。
- 可验证：合成 CDP 快照覆盖 Boss/猎聘未读计数、未识别消息列表时不计数、实习僧等非支持 PC 平台不读取，以及 FastAPI 路由的持久化和审计字段。
- 校准调整：在真实猎聘消息页的只读结构诊断中，发现通用 `ant-im-badge` 同时用于已读和未读联系人，导致初版把 25 个头像误记为未读。探测器改为仅统计 `.im-ui-contact-list-item` 内的 `.im-ui-avatar-weak-unread`，普通 badge 只保留为结构信息，不参与计数。
- 可验证补充：诊断及实际页面回归只读取元素数量、类名、可见性和几何结构，不读取会话正文、名称、标题或链接；单元测试断言猎聘使用校准后的行级显式未读选择器，且不再把 `notification` 当成未读。
- 未验证边界：真实 Boss 与猎聘页面的 DOM 仍需持续积累手动校准样本；当前结果只是“未读标记候选数”，不会自动打开、分类、回复或计入真实沟通成功率。

### 9. 对话式控制不等于暴露模型思维链

- 问题：聊天式 Agent 需要让用户看见任务是否真正执行、用了什么工具和是否触及安全边界，但直接输出模型内部推理既不稳定，也会泄露不应持久化的中间内容。
- 方案：将任务执行拆为可持久化事件：意图判断摘要、工具调用、工具结果和安全结论。前端以持续会话呈现每轮回复及事件，任务通过本地 JSON API 追加，避免页面刷新造成上下文断裂。明确任务先走本地规则，只有规则无法理解时才调用低成本控制层模型。
- 已验证：控制层 API 回归测试覆盖本地统计、受控岗位发现、执行证据持久化以及非 JSON/非对象请求拒绝；搜索任务明确记录“未发送消息、未上传简历、未投递”。`control_intent` 模型任务只接受白名单 schema，测试覆盖有效模型意图、脱敏输入和越权输出回退。
- 边界：模型解析仅用于受限任务理解，网络失败或不合规输出都会回退本地规则；未来应通过真实使用数据比较规则与模型解析的澄清率和误路由率，而不是声称无条件准确。

### 10. 记忆必须可控，不能把推断当作用户事实

- 问题：多轮任务需要保留“当前在处理哪个岗位”等上下文，但自动将聊天、HR 正文或模型猜测写成长时记忆会造成隐私扩张和错误继承。
- 方案：以独立本地表保存两类可控记忆：用户显式选择的当前岗位和用户明确说“记住”的偏好。候选人事实仍以画像/简历为唯一来源；偏好默认不进入外发模型输入，也不自动改变评分，并拒绝保存联系方式和密钥类内容。
- 已验证：聊天可选择岗位、读取当前岗位、生成受准入检查保护的本地投递准备；记忆可在界面编辑、删除，并保留不含偏好正文的审计摘要。
- 边界：当前未做向量检索或对普通聊天的自动记忆提炼，避免在没有明确保留意图时扩大存储与外发范围。

### 11. 聊天式沟通准备不能伪装成真实 HR 对话

- 问题：用户希望由聊天指令直接推进岗位沟通，但在尚未采集真实 HR 对话时，直接生成“回复”会错误暗示对方已经发起联系，且若把草稿放入自主发送队列会绕过对话来源与平台限制。
- 方案：仅在用户显式选择当前岗位或指定岗位编号后，复用投递准备的“建议、风险、状态”准入规则创建本地“聊天沟通准备”草稿。草稿使用确定性的岗位问题模板，不把未证实的技能、项目或 HR 回复写入内容；固定使用草稿模式，不进入自主询问队列。Boss 直聘、猎聘只提示可在现有确认链路中继续处理，实习僧等无 PC 消息能力的平台明确转人工。
- 已验证：端到端测试覆盖缺少当前岗位、低匹配或高风险拦截、合格岗位生成待确认草稿、零浏览器填入/发送调用、零真实对话采集，以及实习僧的人工处理提示；行为日志仅记录草稿元数据、平台能力和提交动作均为 false。
- 边界：该草稿不代表 HR 已读、已回复或愿意沟通；真实消息采集、分类和后续两轮受控沟通仍须在可验证的平台页面中单独发生。

### 12. 将公开公司检索作为受限聊天工具

- 问题：公司风险查询应在用户有投递意向后执行，但若只能从岗位详情页触发，聊天 Agent 无法完成“这家公司怎么样”的常见任务；若在每次 JD 分析时自动查询，又会增加无意义的网络请求和噪声。
- 方案：聊天层只接受当前已显式选择岗位或明确岗位编号的公司风险请求，并复用既有公开来源检索、自动/快速/标准/深度检索规则与来源持久化。每次调用记录来源数量和检索深度，不将搜索摘要交给模型，不访问招聘平台，也不修改岗位评分、投递或沟通状态。
- 已验证：端到端测试覆盖缺少当前岗位拦截、深度查询参数传递、来源保存、招聘平台未访问记录与公司名称缺失时的零网络调用。
- 边界：公开网页搜索结果只是需要人工判断的来源证据，不能推导为公司真实性结论或替代正式尽调。

### 13. 高成本模型工具也需要由工作记忆锚定

- 问题：深度匹配复核会读取 JD 与候选人明确事实并产生 token 消耗。若聊天模型能自行选择某个岗位编号，既可能误用资料，也会让成本和审计对象失去可解释性。
- 方案：只有本地规则从明确岗位编号或显式“当前岗位”工作记忆中解析出目标后，聊天层才调用既有 `job_match` 服务。聊天记录只保存模型标识、返回字段和短结论，详细复核内容继续保存在岗位记录；控制层模型被拒绝输出该工具意图。
- 已验证：端到端测试覆盖未选择岗位的零调用、已选择岗位的复核执行、评分/状态不变、无浏览器与无草稿副作用，以及模型尝试指定岗位时的本地回退。
- 边界：深度复核是补充证据，不能替代本地规则、候选人事实或用户对是否投递的最终判断。

### 14. 聊天式优先级建议不能掩盖证据缺口

- 问题：用户需要在多个候选岗位间决定先沟通哪一个，但让模型直接给出“更好”的结论会把未采集的薪资、公司和 JD 信息伪装成确定判断。
- 方案：岗位比较只读取已保存的本地评分、推荐、风险、薪资和 JD 技能证据；高风险、已归档或“跳过”岗位先降级，再按本地建议和匹配分排序。信息不足时明确返回无优先级，不调用模型或浏览器。
- 已验证：端到端测试覆盖正常比较、当前岗位工作记忆比较、缺失岗位、模型试图指定比较目标时的本地拦截，以及比较前后岗位评分、状态和沟通草稿均不变。
- 边界：它只是在当前本地证据下给出处理顺序，不能代替公司尽调、真实 HR 沟通或最终投递决定。

### 15. 聊天短名单必须与实际岗位状态解耦

- 问题：聊天 Agent 若只会执行搜索或操作单个岗位，用户难以在连续对话中从本地候选集合过渡到复核和沟通；若短名单顺手更新“当前优先”或状态，又会引入未确认的工作流副作用。
- 方案：短名单工具只过滤、排序并返回已保存岗位的编号与现有字段。它保留筛选条件、返回编号和审计记录，但不写入岗位、工作记忆、沟通草稿或投递准备。
- 已验证：端到端测试覆盖高匹配低风险筛选、空结果、模型试图指定筛选对象时的本地回退，以及读取前后岗位评分、状态和草稿数量不变。
- 边界：短名单排序只依据本地规则结果，不能推断公司质量、岗位真实性或未披露薪资。

### 16. 面试准备触发必须晚于人工流程确认

- 问题：对话中出现面试邀请不等于时间、形式和流程已经确认。若聊天指令直接把“面试邀请”变为准备状态，容易把不确定的沟通机会当成既定面试。
- 方案：聊天面试准备工具先读取岗位状态，只有“待面试”或“面试准备中”才能调用既有本地准备服务；其他状态只提示人工确认与手动切换路径。工具不写岗位状态，也不调用模型、浏览器或消息服务。
- 已验证：端到端测试覆盖未确认状态的零创建、已确认状态的创建及重复调用去重、模型尝试指定岗位的本地回退，以及面试时间和岗位状态均不被聊天修改。
- 边界：本地准备材料不代表面试已被接受或时间已锁定，仍需要用户通过招聘平台与 HR 完成确认。

## 后续简历表达候选

以下内容需按自己能解释的深度精简，并以实际代码和验证为准：

- 设计本地求职 Agent 的状态机与安全闸门，将岗位筛选、沟通草稿、投递准备和面试复盘拆为可审计阶段；高风险动作保留人工确认。
- 基于 Edge CDP 构建独立 profile 的受控浏览器读取链路，结合页面身份、控件唯一性和敏感信号校验降低误操作风险。
- 将高频巡检拆为本地文本差分和按需 LLM 复核，无新增内容时不调用模型，减少重复成本与聊天正文暴露。
